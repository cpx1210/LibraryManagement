# 图书馆系统搜索与检测改造路线图

## 目标

本轮优先解决两件事：

1. 馆藏检测不再因为一次扫描过大而超时。
2. 前端能够实时看到检测任务执行进度，而不是只显示“处理中”。

搜索能力重构为 Elasticsearch 先不在本轮落地，本轮先把现有 MySQL + 后端检测链路拆分稳定。

## 当前问题

1. 馆藏检测接口当前会一次性查询馆藏，再同步创建明细并执行检测，数据量上来后容易超时。
2. 检测任务执行时缺少分批处理、缺少已处理数量和批次进度，前端无法展示真实进度。
3. 任务状态虽然有 `pending / processing / success / failed / cancelled`，但没有 `processed_books / current_batch / total_batches` 这类过程字段。
4. 从馆藏发起检测时，旧实现隐含 `LIMIT 10000`，行为不透明，也无法覆盖整馆扫描。

## 本轮实施范围

### 第一阶段：分批检测与实时进度

目标：

1. 馆藏检测按 `10000` 条一批拆分执行。
2. 每批执行后更新任务进度。
3. 前端检测页展示真实进度条、批次号、已处理数量、阶段性统计结果。

实施项：

1. 给 `booklist_check_task` 增加字段：
   - `processed_books`
   - `current_batch`
   - `total_batches`
2. 新增馆藏检测创建服务：
   - 先统计命中总量
   - 再创建总任务
   - 然后启动异步分批执行
3. 新增异步执行器：
   - 上传书单检测按批处理已有明细
   - 馆藏检测按条件分页读取馆藏并分批写入结果明细
4. 前端 `书单检测` 页支持：
   - 根据 `taskId` 查看单个任务实时进度
   - 自动轮询
   - 展示进度百分比、已处理数量、批次进度

预期结果：

1. 不再出现整馆检测同步超时。
2. 用户能看到“第几批 / 共几批、已处理多少本”。
3. 任务失败或取消时，页面能停留在当前进度。

### 第二阶段：检测链路继续提速

目标：

1. 降低单本检测时的数据库往返次数。
2. 为后续整馆或增量检测留出性能空间。

实施项：

1. 敏感词、问题书目、白名单在任务开始时预加载。
2. 敏感词匹配从逐条数据库查询，改为内存匹配。
3. 问题书目优先走 ISBN 精确命中。
4. 明细写入从“逐条 update”逐步改为更批量的写法。

预期结果：

1. 每批 10000 条的执行耗时进一步下降。
2. 全量检测总时长明显缩短。

### 第三阶段：搜索能力重构

目标：

1. 支持任意字段模糊搜索与多字段联合搜索。
2. 减少 MySQL 上 `%LIKE%` 的压力。

建议路线：

1. `MySQL -> Canal -> Elasticsearch`
2. 搜索接口单独走 ES
3. 检测类离线扫描继续保留后端批处理链路

说明：

这一阶段不在本轮代码改动范围内，等第一阶段稳定后再单独推进。

## 本地开发到内网上线建议

1. 本地先完成代码与 SQL 升级。
2. 本地验证：
   - 馆藏检测任务创建成功
   - 任务进度能实时刷新
   - 任务完成后可查看结果
3. 整理交付物：
   - 后端代码
   - 前端代码
   - 数据库升级 SQL
   - 构建与回滚说明
4. 再传到内网服务器进行构建、打包镜像和导入。
